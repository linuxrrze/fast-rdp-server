# A5: capture of 2026-10-26 (mstsc, second *Connect* black)

Findings of one lab run for [backlog A5](backlog.md) (the next *Connect* in the same mstsc
shows a black window instead of the waiting screen), kept for further analysis. Test plan:
[lab-waiting-screen-input.md](lab-waiting-screen-input.md) F19c. The raw files stay out of
git (they decrypt the whole run).

- fast-rdp-server 0.7.7, F19c run 1 (`WaitingScreenObserve` off), `TlsKeyLogFile` on.
- mstsc on Windows: client `DESKTOP-AALN4PJ`, build 26100, 1280x800, gfx yes, dynvc yes.
- User `testuser`, Kerberos NLA (mstsc first requests Kerberos user-to-user), MFA mode

- Files: `tcpdump` capture, the `ss` loop, the TLS key log, the proxy journal and mstsc's
  *ClientActiveXCore* event log, as in
  [lab-waiting-screen-input.md §3](lab-waiting-screen-input.md#3-capturing-input-without-leaking-codes).
  Kept locally in `debug/a5` (git-ignored), not in the repository.

Pattern: the window is black exactly when the previous connection in the same mstsc
process used GFX. How that connection ended (the X or a logout) does not matter, and a
connection without GFX (C2, which never got past the waiting screen) resets it: C3 shows
the panel again. The same happened earlier that day (19:17 and 19:19, before the key log
was on): a session, then a black second connection that the user closed after 14 s.

## Evidence

The capture was decrypted (TLS 1.3 with the key log) and decoded in both directions
(Method, below).

- MCS Connect Initial and Confirm Active are byte-identical in C1 to C4. The Client Info
  PDU differs only in 2 bytes (security header `flagsHi`, offset 17–18 of the TPKT PDU),
  identically in C2, C3 and C4, so it is not the cause.
- In C2 and C4 the proxy sends the same waiting screen fast-path Bitmap Updates as in C1
  and C3 (one compressed, fragmented update per second for 90 s, about 138 kB). mstsc
  acknowledges them: no zero window, no stall.
- During the wait mstsc sends only fast-path input: no Refresh Rect, no Suppress Output,
  no Shutdown Request. So `WaitingScreenObserve` has nothing to answer.
- Only in C2 and C4 mstsc sends a burst of input (a QoE timestamp, 10 scancodes, a
  synchronize event, a mouse event) between Control Request and Font List, i.e. before it
  has finished the activation: a sign of state carried over from the previous
  connection.
- mstsc's event log shows nothing for C2 and C4 beyond the connect (1025) and the
  disconnect reason 2.

## Hypothesis

mstsc keeps GFX output state across connections in one process and shows legacy bitmap
output black afterwards [inferred: Windows servers draw even the logon screen over GFX,
so this path is probably untested in mstsc]. Not verified yet. In the working connections
the proxy reactivates the client when the back-end takes over (Deactivate All, Demand
Active), and mstsc rebuilds its display then.

## Run 2: reactivation before the panel

Same setup on fast-rdp-server 0.7.8 with `WaitingScreenReactivate=true` (key log on,
capture decrypted). mstsc had been restarted before C1.

| Connection | Previous connection in this mstsc | Result |
|---|---|---|
| C1 20:57:22 | fresh mstsc | reactivation in 24 ms, panel OK, approved; session 4 s with GFX (event log 1402/1401), X |
| C2 20:58:10 | C1 (GFX) | reactivation in 17 ms, **black** for the whole wait, MFA timeout after 90 s |

- The reactivation completes on both sides: after Font List the proxy sends Deactivate
  All + Demand Active, mstsc answers with Confirm Active, Synchronize, Control (Cooperate,
  Request Control) and Font List; mstsc's event log has "connected" (1025) twice per
  connection. Then the proxy sends the same waiting-screen Bitmap Updates as in C1
  (97 updates, about 138 kB). mstsc still shows black: the state carried over from a GFX
  connection survives a reactivation.
- The input burst (QoE timestamp, 10 scancodes, sync, mouse) before Font List is what
  mstsc sends on a **re**activation: in C1 it appears only after the proxy's reactivation,
  in C2 (and in run 1's C2/C4) already at the first activation. mstsc treats the first
  activation of a new connection like the reactivation of the previous one, which
  supports the carried-over-state hypothesis.
- FreeRDP logs the expected tpkt "got 0" warning with a backtrace and a
  `transport_check_fds` error per reactivation (see backlog A5; gone with
  fastrdp-freerdp3 3.32.2-8, which ends the rerun without a read).

Manual check during a black C2 (2026-10-26): resizing the mstsc window repaints
nothing at all, not even black (the window area keeps whatever was there). A resize is
repainted by mstsc from its own copy of the screen, without the server, so mstsc does not
present the surface the legacy Bitmap Updates go to: not a missing repaint from the
server (Refresh Rect and the reactivation are ruled out anyway), but mstsc's output still
bound to the GFX pipeline of the previous connection [inferred]. Still open: the GFX-off
experiment (1. above) as confirmation; then [backlog A8](backlog.md#maybe-later).

## Process ids in the event log

`evtx_summary.py` on the two event logs (2026-10-26) shows the process id of mstsc per
connection: run 1 C1 and C2 ran in process 7448, C3 and C4 in **7488**; run 2 C1 and C2
in 3992; the earlier pair at 19:17/19:19 in 3156. So in run 1 C3 started in a new mstsc
process, not "in the same process" as the table above says, and the observation "a
connection without GFX resets it" (C3 working after the black C2) is not supported by
run 1: every black connection is the second one in its process after a GFX connection,
every working one the first in its process. How C3 got a new process (mstsc restarted by
hand, or mstsc starting one itself after the timeout) is not known [inferred: the notes do
not say]. Check in the next run: after a black connection, *Connect* again in the very same
window, and note the process id (event log) of each connection.

## Spec check (2026-10-27)

The Microsoft specifications (MS-RDPBCGR, MS-RDPEGFX, MS-RDPEDYC, MS-RDPRFX, MS-RDPEDISP,
current versions) and the sources of FreeRDP 3.32.2 and xrdp 0.10.6.1 checked for an
explanation, also of [A9](backlog.md#sessions) and [A10](backlog.md#sessions).

A5:

- **Nothing in the specification explains it.** The client's GFX state is defined per
  connection (MS-RDPEGFX 3.3.1: contexts kept "for the duration of the RDP connection");
  no rule lets a client keep state across connections, none forbids legacy output to a
  client that supports GFX; after a Shutdown Request Denied the client's behaviour is
  "implementation-dependent" (MS-RDPBCGR 1.3.1.4.1). The 2 bytes in which the Client
  Info PDUs differ (`flagsHi`) "MAY contain random data" (2.2.8.1.1.2.1): noise.
- **The GFX-off first try probably counted.** With `[Channels] GFX=false` FreeRDP's proxy
  sets `SupportGraphicsPipeline` off before the negotiation (`pf_server.c:548`), so its
  negotiation response does not offer GFX, and it intercepts drdynvc
  (`pf_context.c`, `dyn_intercept()`): mstsc could not start GFX in connection 1, and
  connection 2 was still black [inferred from the source; the event log of that run is
  missing, item A of the checklist confirms it]. So "the previous connection had a
  session" (the hand-over with its reactivation, the session's channels, how it ended)
  fits better than "the previous connection had GFX".
- **Why mstsc may never meet this elsewhere** [inferred]: xrdp draws even its own login
  screen over GFX once drdynvc is up, gnome-remote-desktop dropped its legacy path, and
  Windows servers draw the logon screen over GFX. Legacy Bitmap Updates to a GFX-capable
  mstsc, before any dynamic channel exists, are probably a path mstsc is hardly tested
  on. That keeps [A8](backlog.md#maybe-later) (the waiting screen over GFX) a candidate,
  no longer a certain one.
- **Ruled out by the spec and the captures:** the negotiation flags and early capability
  flags (identical in good and black connections), Refresh Rect and Suppress Output, the
  Set Error Info code (0x1 vs 0xC), the Monitor Layout PDU.
- **Experiment:** connection 1 with drdynvc blocked entirely, not only GFX
  ([lab-checklist-0.7.6.md §1](lab-checklist-0.7.6.md#1-a5-mstsc-reconnect-in-the-same-process-priority)
  item F): black connection 2 then rules out every dynamic channel.
- **Workaround idea, self-redirection** (low confidence): the input burst before Font
  List at the *first* activation marks an mstsc carrying state over (Run 2). For such a
  client only, the proxy would send a Server Redirection PDU pointing at itself; the
  client "MUST terminate the current connection … and initiate a new connection"
  (MS-RDPBCGR 3.2.5.13.1). This only helps if a new connection *in the same process*
  clears the state, which run 1 does not show (C3 was a new process). Item A of the
  checklist (*Connect* again in the same window after the black connection) decides
  whether the idea is worth building; far smaller than A8 if it is.

A9 (xfce over GFX RemoteFX Progressive, stale or wrong rectangles):

- MS-RDPEGFX allows tiles to carry pixels outside the region (2.2.4.2.1.5), and keeps
  the client's per-tile coefficient state for sub-band diffing (3.2.8.1.4, 3.3.1.3).
- **Main suspect** [inferred, medium]: xorgxrdp's `rdpCaptureGfxPro()` zero-fills a
  partially changed 64×64 tile (Y=U=V=0, with the +128 chroma offset a saturated dark
  green) and converts only the changed rectangles into it; xrdp's encoder compresses the
  whole tile with loss, and the quantization error of the green part reaches the visible
  pixels near the edges. Window moves make many such tiles; the tile-hash skip then keeps
  the wrong pixels until the area changes again. The H.264 capture has no zero fill,
  which fits H.264 being clean. Lab build: `fastrdp_xorgxrdp_lab_gfxpro_fill_tiles`
  (`patches/xorgxrdp-lab/0002`, checklist item E); quick check without a build: the
  glitches grow with a coarser quantization (`modem` vs `lan` profile).
- Second suspect: the tile-hash skip together with a lost or changed tile
  (`patches/xorgxrdp-lab/0001`). Third: librfxcodec's sub-band diffing (xrdp never
  resets the reference state on the GFX path); a lab build without diffing would test
  it.

A10 (xfce black with GFX off):

- Codec ids are assigned by the client (MS-RDPBCGR 2.2.7.2.10.1.1: "the client
  determines the 8-bit ID"). The proxy's back-end hop announces RemoteFX and NSCodec to
  xrdp under FreeRDP's fixed ids (3 and 1, `capabilities.c`), and the surface bits xrdp
  sends with them reach mstsc unchanged; nothing maps them to mstsc's own ids. A second
  candidate: xrdp sends the RemoteFX data as Stream Surface Bits, which MS-RDPBCGR says
  RDP 10.12 and later clients do not support (footnote <37>; contested by IronRDP's
  tests on Windows 10).
- Quick check: `[Codecs] RFX=false NSC=false` (xrdp falls back to plain bitmap
  updates; checklist item G). The proper fix would be in the proxy or the module:
  translate the codec ids, or announce to the back-end only codecs the client has.

## Open-source projects (2026-10-27)

Trackers and sources of open-source RDP servers and proxies (FreeRDP, IronRDP, xrdp,
gnome-remote-desktop, ogon, weston, warpgate, macrdp) and Microsoft Q&A, checked for A5
and what others do before a session exists.

- **Nobody reports A5 itself** (black legacy output on the next *Connect* in the same
  mstsc process): nothing on GitHub, GNOME GitLab or Microsoft Q&A. xrdp's reconnect
  black screens (#1964, #3543, #1636, #2968) are server-side session problems
  [verified: titles and snippets only].
- **Closest report: macrdp [#229](https://github.com/clintcan/macrdp/issues/229) /
  [PR #230](https://github.com/clintcan/macrdp/pull/230)** (Windows 10 mstsc
  10.0.19041.4717): if one legacy Bitmap Update reaches mstsc before EGFX is ready, "the
  client stays on the legacy picture": it acknowledges every H.264 frame and never
  presents GFX. Holding legacy output until EGFX is up (or declined, or 3 s) fixed it:
  frozen starts 8/8 → 0/8 [verified: issue and PR]. Same class of fault as A5 (mstsc does
  not switch cleanly between legacy and GFX output within one connection), opposite
  direction, not the same trigger [inferred].
- **ogon** (the one open-source greeter/session hand-over on a FreeRDP server):
  "If settings->SupportGraphicsPipeline is true the clients may refuse to display rfx
  sent in the surface command", so ogon draws its greeter over GFX for every client with
  GFX and drdynvc, legacy only for the others [verified:
  [ogon](https://github.com/ogon-project/ogon) `rdp-server/frontend.c:482-490`]. And:
  "the Microsoft clients always terminate with a protocol error if the gfx channel is not
  recreated after a reactivation", so ogon closes and reopens its GFX channel around every
  activation [verified: `frontend.c:579-594`]; this is the rule for
  [A8](backlog.md#maybe-later): the proxy's own GFX channel must be closed before the
  hand-over reactivation.
- **Every GFX-capable server holds legacy output back** from a client that announced GFX:
  xrdp 0.10 queues dirty regions for GFX and sends nothing until EGFX is up [verified:
  xrdp 0.10.6.1 `xrdp/xrdp_painter.c:96-100`]; FreeRDP's shadow server sends no surface
  update until the GFX channel is open and its caps are confirmed [verified: FreeRDP
  3.32.2 `server/shadow/shadow_client.c:2314-2345`]; gnome-remote-desktop deprecated and
  removed its legacy path
  ([MR 136](https://gitlab.gnome.org/GNOME/gnome-remote-desktop/-/merge_requests/136),
  [MR 274](https://gitlab.gnome.org/GNOME/gnome-remote-desktop/-/merge_requests/274))
  [verified]; Windows draws its logon screen over GFX; weston sends legacy output but never
  announces GFX. Only our proxy sends legacy Bitmap Updates while its RDP_NEG_RSP offers
  GFX [inferred from the above]. This strengthens A8 again; the GFX-off first try (above)
  still has to be repeated with evidence.
- **Windows 11 24H2 Bitmap Update bug,
  [FreeRDP #10413](https://github.com/FreeRDP/FreeRDP/issues/10413):** 24H2 mstsc (26100)
  before 26100.3194 (fixed by KB5051987, February 2025) mishandles Bitmap Updates with
  several rectangles (only a few squares drawn) [verified: issue]. The waiting screen sends
  several per update (`ws_flush()` in `fastrdp_plugin.c`). Unlikely the cause, since C1
  renders [inferred]; the lab client's exact build (`winver`, 26100.x) goes into the notes
  ([lab-checklist-0.7.6.md §1](lab-checklist-0.7.6.md#1-a5-mstsc-reconnect-in-the-same-process-priority)).
- **Save Session Info:** the proxy only forwards the back-end's (`pf_update.c:301-332`)
  and sends none of its own [verified: FreeRDP 3.32.2]; xrdp sends one only from its
  neutrinordp module (xrdp as RDP proxy), the Xorg module never calls
  `server_session_info` [verified: xrdp 0.10.6.1 `neutrinordp/xrdp-neutrinordp.c:2494-2555`,
  `xrdp/xrdp_mm.c:4414-4420`, no call in `xup/xup.c`]; stock gnome-remote-desktop sends
  none (only an out-of-tree patch,
  [Pave87/gnome-remote-desktop-logonnotify](https://github.com/Pave87/gnome-remote-desktop-logonnotify))
  [verified]. So mstsc never got a logon notification in C1–C4. The only documented effect
  of its absence is a missing connection-history entry; C1 works without it, so it cannot
  be the sole cause [inferred]. ([rdp-spec-conformance.md §3](rdp-spec-conformance.md#3-client-info-pdu-and-the-credential-swap-ms-rdpbcgr-22111)
  corrected.)
- **Auto-reconnect cookie ruled out:** nobody in the chain issues one (it would come in a
  Save Session Info), and the Client Info PDUs of C1–C4 differ only in `flagsHi`; a cookie
  would add at least 28 bytes [verified: [Evidence](#evidence)].

Ranked ideas:

1. Lab first: items A, G and F of the
   [checklist](lab-checklist-0.7.6.md#1-a5-mstsc-reconnect-in-the-same-process-priority),
   the client's exact build (`winver`), and a fully patched Windows 11 or the Windows App

2. A8: the waiting screen over GFX, legacy output only as a fallback for clients without

## Method

A pcap reader with TCP reassembly per client connection (retransmissions dropped), TLS 1.3
record decryption with the secrets of the NSS key log (traffic keys with
HKDF-Expand-Label, RFC 8446 7.1; handshake secret, then the first application secret),
and an RDP decoder for what comes out: CredSSP TSRequests by size, X.224, MCS (Connect
Initial/Response, Attach User, Channel Join, Send Data, Disconnect Provider Ultimatum with
its reason), the security-header PDUs (Client Info, licensing), share control and share
data PDUs by type (with the Set Error Info code and the Control action), fast-path input
by event class and fast-path output by update type, and the static channels by name, with
the DVC Create names on `drdynvc`. Repeats of the same PDU collapse into one line.

The scripts are in `tests/lab/rdpcapture/` (standard library plus python3-cryptography;
offline tests in `tests/lab/test_rdpcapture.py`, part of `make test-lab`):

```
tests/lab/rdpcapture/decode.py a5-run1.pcap a5-run1-keys.txt [--port 3389]
```

It prints one timeline per TCP connection, in seconds since its first packet:

```
===== 192.168.1.106:62846 19:37:10
   6.696 C>S Data Control action=RequestControl
   6.696 S>C Data Synchronize
   6.696 S>C Data Control action=Cooperate
   6.696 S>C Data Control action=Granted
   6.696 C>S FP-in qoex1,scancodex10,syncx1,mousex1
   6.696 C>S Data FontList
   6.696 S>C Data FontMap
   6.704 S>C FP-out bitmap/frag2/comp
```

`--summary` prints one line per connection (channels, the DVCs mstsc accepted, the
reactivations, Bitmap Updates before the back-end session, how it ended), `--compare N M`
what differs between two of them (for the client's Core Data and Confirm Active only the
offsets); `evtx_summary.py` summarises mstsc's exported event log per connection, with
the mstsc process id. The collection on the proxy host: `tests/lab/a5-collect.sh`.

It prints PDU names, sizes and protocol fields only, never key material or payload bytes;
connections without secrets in the key log are listed as such. TLS 1.3 only; key updates
are not followed. The key log and the capture together decrypt everything (a code typed
into the waiting screen, a TLS password): lab users only, delete both after the analysis.
